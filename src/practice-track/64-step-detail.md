## Step detail

- Every step is complete: exact menu paths and field values; node, class, API or command names; code with its file, anchor and the lines to add, replace or delete; and the expected result after each meaningful step. Detail does not fade with repetition.
- Only trivial actions are written briefly: saving, compiling, switching to a window the plan just named, starting a run the plan has already shown. When unsure whether an action is trivial, write it out.
- Never write a step as a goal that assumes knowledge from an earlier plan ("set up movement like before", "add an interaction system"). Anything built in an earlier plan is written out again in full; the toolbox entry is linked for background.
- Design choices (layout, values, names, structure) are supplied by the plan, ready to type; the user never has to invent them.
- A concept met in an earlier plan gets a one-line reminder and a toolbox link instead of a full explanation; its steps are still complete.
- When a step fails, the reply names the likely cause and the fix directly; a fix that changes the plan is added to it as a fix step.
